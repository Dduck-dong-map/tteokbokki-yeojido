## 7. 검토 결과

### 7-1. Architecture

**두 형태 비교(design-twice)** — 새 경계 = "화면 컴포넌트"의 공개 면.
- 형태 1 (지금): 화면 파일 하나가 마크업+상태+데이터 가공 (`MapShell.tsx` 376줄 `"use client"`, `RegisterForm.tsx` 384줄). 인터페이스는 얕고(props 거의 없음) 안은 크다.
- 형태 2 (선택): `X.tsx` 컨테이너(상태·fetch·라우터) + `XView.tsx`(props → JSX). View 의 공개 면은 props 타입 하나, 안에 레이아웃·반응형·접근성을 숨긴다. **더 깊은 모듈**이고 에이전트 분담(마크업 전문 / Next 전문)과 1:1 로 맞는다(Conway).
- 선택 이유: 마크업 에이전트가 "상태·이벤트를 구현하지 않는다"는 제약을 **파일 경계로 강제**할 수 있다. 형태 1 로는 같은 파일을 두 에이전트가 만져 split ownership(빨간 깃발 5).

**빨간 깃발 점검:**
- (5) split ownership → View/컨테이너 파일 분리로 해소. (6) 두 방법 — 토큰 두 벌(R2 보류) → 3절 공존 규칙 + 지름길 표시. (8) 손으로 맞추는 목록 — `NAV` 가 `SiteHeader`·`BottomNav` 둘 다 쓰나 `ui.tsx:113` 한 곳 정의 → `layout/nav.ts` 로 이동, 통과. - "라우트 10개"의 선정 기준이 없다. 저장소에는 page.tsx 라우트가 23개 있고 어드민도 포함된다. 어떤 10개를 검증할지, 나머지 동적·중첩 라우트가 왜 안전한지 계획에서 알 수 없다.
- 병렬 분담은 계약 정의 단계에서 직렬화된다. View 의 props 를 컨테이너 담당자가 먼저 정해 마크업 담당자에게 넘겨야 한다. 화면마다 그 계약이 확정될 때까지 병렬 작업은 시작할 수 없다. 이 대기와 계약 변경에 따른 재작업이 공수·일정 추정에 반영되지 않았다.
- 모든 화면을 컨테이너/View 두 파일로 나누는 비용이 정당화되지 않았다. 상태와 마크업이 밀접한 폼·관리자 화면까지 일률 적용하면 props 와 파일만 늘 수 있다. 적용 기준이 없다.
- 5.5~6시간 추정은 계획의 작업량과 맞지 않는다. 99개 TS/TSX 이동, 23개 페이지, 12개 UI 부품, 화면 재작성, API·설정 병합, 24개 테스트 공백을 한 PR 에서 처리한다. "화면당 25분"에 기존 동작 파악·View 계약 조율·반응형 회귀 수정이 어떻게 들어가는지 설명이 없다.
