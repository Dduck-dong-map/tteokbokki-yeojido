## 3. 구조 정리 제안

### 3-1. `db.ts` 659줄 → 책임 4개로 분리
**현재:** 한 파일이 다음을 모두 가진다.
- 저장소 I/O: `load`(92)·`save`(102)·`mutate`(119)·PG 분기(89 `const PG = !!process.env.DATABASE_URL`)
- 시드: `withCommunity`(54)·`seed`(70)
- 신원·한도 규칙: `hash`(131)·`mark`·`same`·`overDailyLimit`(140)
- 가게 도메인: 읽기 149~170, 쓰기 172~421 (`addStore`·`editStore`·`confirmStill`·`verifyStore`·`reviewStore`·`flagStore`·`flagReview`)
- 게시판 도메인: 423~566 (`readPosts`…`flagComment`)
- 리스트 도메인: 568~659 (`createList`…`likeList`)
파일 안 구분선 주석(`// ───────── 읽기 ─────────` 147, 423 이 두 번 나옴)이 이미 경계를 말해 준다.

**제안:** `data/store.ts`(저장소 I/O + 시드 + `Db` 타입), `data/stores.ts`, `data/posts.ts`, `data/lists.ts` 로 나누고 `data/index.ts` 가 지금처럼 묶어 내보낸다. `pg.ts` 는 `Db` 타입만 import 하므로 그대로.
**왜:** 명시성. 라우트 5개가 import 하는 함수가 어느 도메인인지 파일 이름으로 보인다. `db/README.md` 의 "규칙은 db.ts 한 곳" 약속은 `data/` 폴더 한 곳으로 바뀔 뿐 깨지지 않는다.
**공수:** 사람 ~반나절 / CC ~20분. 동작 변화 없음(이동만). **tsc 가 모든 import 경로를 잡아 주므로** 위험 낮음.

### 3-2. API 라우트의 `reply` 헬퍼 3중 복제
**현재:** 같은 6줄이 세 파일에 있다.
- `src/app/api/stores/[id]/route.ts:13-14`
- `src/app/api/room/route.ts:10-11`
- `src/app/api/lists/[id]/route.ts:11-12`
```ts
const reply = (res: { ok: true } | { ok: false; error: string; status: number }) =>
  res.ok ? Response.json(res) : Response.json({ ok: false, error: res.error }, { status: res.status });
```
`lists/route.ts:17` 와 `stores/route.ts:16` 은 같은 일을 인라인으로 한 번 더 쓴다(후자는 `existing` 필드를 더 넘기므로 살짝 다름).
그리고 다섯 라우트 모두 첫 두 줄이 같다: `const body = await readJson(req); if (!body) return bad("내용을 읽지 못했어요");`.

**제안:** `src/lib/request.ts` 에 `reply` 를 옮기고(이미 `bad`·`readJson`·`whoFrom` 이 거기 있다), `Fail` 타입(`db.ts:570 … | Fail` 에 이미 있음)을 `request.ts` 또는 `types.ts` 로 올려 라우트와 db 가 같은 타입을 쓴다.
**왜:** DRY. 응답 모양이 바뀌면(예: 에러 코드 추가) 다섯 곳 대신 한 곳.
**공수:** 사람 ~30분 / CC ~5분.

### 3-3. `StoreList.tsx` vs `home/StoreRow.tsx` 카드 본문 반복
**현재:** 이름·확인 중 배지·동·확인 시각·태그·별점·맵기 도장·가격 블록이 두 파일에 거의 같은 JSX 로 있다.

**왜:** DRY. 10-28 슬랙에서 정한 "정보 순서" 가 바뀌면 지금은 두 곳을 같이 고쳐야 한다.
**공수:** 사람 ~1시간 / CC ~10분. 화면 회귀 확인은 `/list` 와 `/` 두 곳.

## 6. 보류 (확신도 4 이하, 참고용)
