## 문제 정의

떡볶여지도는 1차 MVP 코드가 끝났고(반응형 웹 · 등록 · 상세 · 길찾기 + 2차 게시판·리스트 · 도커 DB), **이제 배포해서 청년부가 쓰게 하는 단계다** (사용자 11-09: "1차 MVP 라 사용자가 없는 게 당연하다. 이제 배포하고 쓰게 할 예정"). 그래서 이 문서의 질문은 "왜 안 쓰이나"가 아니라 **"배포해서 쓰게 하려면 지금 무엇이 막고 있고, 첫 2주에 무엇을 보나"**다.

배포를 막는 것은 세 가지다: ① Vercel 에서 저장이 안 된다(파일 저장소 → Supabase 필요) ② 가게가 예시 16곳(가짜)이라 열어도 갈 곳이 없다 ③ 사진이 서버 폴더라 Vercel 에서 사라진다. 문서 세 곳(기획안 13절 · 시장조사 결론 · MVP 구도)이 ②를 가장 큰 위험으로 적어 두었다.

## 수요 증거 (Q1)

- 답: **아직 없다 — 배포 전이라 당연하다.** 팀장·팀원 피드백 2회(10-28, 11-02)는 관심. 배포 뒤 첫 2주에 아래 「성공 기준」으로 처음 잰다.
- 누군가 "지도 주소 다시 주세요"라고 먼저 물은 기록 없음.
- 판단을 바꿀 증거: 청년부 누군가가 실제로 지도를 보고 가게에 간 사례 1건.

## 현재 방식 (Q2)

- 답: **네이버·카카오 지도에서 "떡볶이" 검색.**
- 그 방식의 짜증 포인트(프랜차이즈가 덮는다 / 맵기를 모른다 / 어디가 진짜인지 모른다)는 **아직 팀원 입으로 확인한 적이 없다.** 기획안 4절의 "SNS → 지도 두 단계" 문제는 거지맵 기사에서 온 말이다.

## 대상 사용자 (Q3)

- 범주: **교회 청년부(3청).** 기획안의 "3청의 미식 지도"가 이것.
- 그 안에서 폰을 쥐어 줄 **첫 한 사람은 미정.** 사용자가 "이 부분은 신경 안 써도 된다"고 해 더 좁히지 않았다. 설계는 "청년부 전체"가 아니라 "청년부에서 가장 자주 떡볶이집을 찾는 1~3명"을 전제로 쓴다.

## 전제 (Phase 3)

| # | 전제 | 상태 |
|---|---|---|
| 1 | 지금 가장 큰 위험은 기능 부족이 아니라 **핀이 비어 있는 것**이다 | **부분 동의** (사용자): 데이터가 먼저지만 게시판 같은 기능도 같이 가야 팀이 모인다 |
| 2 | 지도의 첫 가치는 "청년부가 자주 가는 동네의 실제 가게"다. 마포·서대문 300곳(기획안)보다 **청년부 동선 30~50곳**이 먼저다 | 사용자 확인 전 (제 판단) |
| 3 | 11-08 에 들어간 게시판·리스트는 팀 결정(10-28 "커뮤니티는 2차")과 어긋난다. 남기되 **팀에 알리고**, 데이터를 만드는 통로("같이 가요" 글마다 가게 1곳)로 쓴다 | 사용자 확인 전 (전제 1 부분 동의를 반영한 절충) |

## 1차 MVP 평가 (사용자 요청)

**잘된 것**
- 거지맵 구도("모두가 고치는 지도": 찾기 → 등록 → 검증 → 갱신)를 **코드로 끝까지 돌게 만들었다.** 등록·바로 공개·7일 확인 중·맞아요/달라요·이력·신고가 실제로 저장된다. 이건 거지맵 기사만 읽고는 못 만드는 수준이다.
- 규칙(`wiki.ts`)과 저장(`db.ts`/`pg.ts`)을 분리해 Supabase 전환이 `DATABASE_URL` 하나로 끝난다. 11-09 도커 시험 기록이 꼼꼼하다.
- 반응형 3단 틀, 대동여지도 지도, 맵기 게이지 도장, 호랑이 로딩 — 팀 피드백을 빠르게 반영했고 개성이 분명하다.
- `tsc`·`eslint` 오류 0. 문서화 습관(ADR, 관문, 시험 기록)이 1인 프로젝트치고 매우 좋다.

**배포 전에 걸리는 것**
- **실제 가게 0.** 배포해도 열면 가짜 16곳이라 갈 곳이 없다. 첫 핀 30곳이 배포와 같이 가야 한다.
- 배포 순서상 W3(Supabase) 가 도커까지만 왔다. Vercel 에 올리면 저장이 화면에 안 나타난다(웹1차기획 4.1 확인). 2차 기능이 먼저 들어온 건 배포 뒤 쓰일지 볼 수 있으니 문제가 아니라 **배포가 늦어진 것**이 문제다.
- 팀 결정과 어긋난 것 3개(커뮤니티 2차 / 어드민 추후 / 맵기 투표 보류)가 **11-02 이후 팀에 공유되지 않았다**(웹1차기획 I-05 "답 대기").
- 팀 main 과 공통 조상이 없는 브랜치 문제(정-1)가 11-02 부터 그대로다. 합치는 날 팀원 파일이 지워진다.
- 핵심 지표 KPI-W01(주간 길찾기)을 재는 코드가 없다. 성공했는지 알 방법이 없다.
- 공개 전 필수 6건(어드민 무인증, HASH_SALT 기본값, 기기 헤더 신뢰, 사진 로컬 저장, USING_SAMPLE_DATA 하드코딩, 캡차 없음) — 별도 기술 검토 보고서 2절.

**한 줄 평:** 1차 MVP 로서 엔진은 충분하다. 배포에 필요한 건 새 기능이 아니라 Supabase 연결·첫 핀 30곳·사진 처리 셋이고, 전부 합쳐 코드는 CC ~1시간, 데이터는 팀 2~3일이다.

## 대안

### A. 핀 먼저, 기능 동결 (최소안) — 추천
- 요약: 2주 동안 새 기능 0. 청년부 동선의 실제 가게 30~50곳을 넣고, Supabase 에 연결해 Vercel 에 올리고, 팀원 1명에게 폰을 쥐어 주고 지켜본다. 게시판·리스트는 **그대로 두되 홍보하지 않는다.**
- 공수: S~M (데이터 수집은 사람 2~3일 / 코드 CC ~1시간: Supabase 연결·`USING_SAMPLE_DATA` 환경변수화·HASH_SALT 가드)
- 위험: 낮음
- 장점: Q1 의 "사용자 0"을 깨는 가장 짧은 길 · 이미 만든 코드가 그대로 가치를 낸다 · 팀장 피드백 "다음 주 완성 · 기능보다 사용 편의"와 맞는다
- 단점: 데이터 입력은 지루하고 팀의 손이 필요하다 · 2주간 눈에 보이는 "새 화면"이 없다
- 재사용: 등록 화면(`/register`) 그대로, 도커 → Supabase 절차(`web/db/README.md`) 그대로, 어드민 표 파일 올리기(REQ-AW09)는 아직 없으니 처음 30곳은 `/register` 로 직접 넣거나 시드 JSON 교체

### B. 기획대로 완주 (이상안)
- 요약: 웹1차기획 W2 어드민 연결 → W3 Supabase·로그인·사진 Storage·주소 검색 → W4 300곳·약관·캡차·폰 실기 → W5 베타 2주 → 공개.
- 공수: XL (CC 로도 3~4주, 데이터 300곳은 팀 2~3주)
- 위험: 중간~높음 (완성될 때까지 사용자 0 이 계속된다)
- 장점: 공개 출시까지 빠진 게 없다 · 운영 통제 수단이 먼저 생긴다
- 단점: 지난 2주와 같은 패턴 — 끝날 때까지 아무도 안 쓴다 · 청년부용 지도에 300곳·캡차·약관은 과하다
- 재사용: 전부

### C. "같이 가요"가 입구 (다른 관점)
- 요약: 지도가 아니라 **게시판 "같이 가요" 글**을 청년부 입구로 삼는다. 모임 글을 쓰면 가게 1곳을 함께 등록하게 해서, 데이터가 사용에서 자란다. 지도는 그 결과물.
- 공수: M (글쓰기 ↔ 등록 연결 CC ~반나절)
- 위험: 중간 (청년부가 게시판을 쓸지는 지도만큼이나 미확인)
- 장점: 전제 1 의 "부분 동의"(기능도 같이)를 가장 정직하게 살린다 · 데이터 입력이 숙제가 아니라 모임 준비가 된다
- 단점: 카톡 단톡이 이미 그 역할을 한다 — 상태 유지(현재 방식)와 정면 경쟁 · 사용자 0 인 지금 두 가설을 동시에 시험하는 셈

## 추천

**A.** 이유: Q1~Q3 답(사용자 0 · 현재 방식 네이버 · 첫 사용자 미정)에서 가장 싸게 배우는 길이다. 전제 1 의 "부분 동의"는 **C 를 A 다음 2주의 후보**로 두는 것으로 받는다: A 로 가게 30곳과 첫 사용자 1명이 생기면, 그 사람이 "같이 가요"를 쓰는지 보고 C 를 켠다. 두 가설을 한 번에 시험하지 않는다.

A 에서 코드로 할 일 (전부 CC ~1시간, 기술 검토 보고서 2절·8절 참조):
1. Supabase 프로젝트 만들기(사람) → `DATABASE_URL` → Vercel 배포
2. `USING_SAMPLE_DATA` 환경변수화 (`web/src/lib/data/index.ts:35`)
3. `HASH_SALT` 프로덕션 가드 (`web/src/lib/data/db.ts:132`)
4. `direction_click` 이벤트 1개만 기록 (KPI-W01) — Vercel Analytics 커스텀 이벤트, 코드 5줄
5. 예시 가게 16곳 제거(`isSample` 가게 숨김)

## 열린 질문

- 청년부에서 **첫 한 사람**은 누구인가 (이름). 이 사람이 정해져야 "청년부 동선 30곳"의 동네가 정해진다.
- 전제 2·3 에 동의하는가.
- 팀 공유(I-05): 커뮤니티 2차 → 들어옴 / 어드민 추후 → 시안만 / 맵기 투표 보류. 슬랙 초안 필요 여부.
- 정-1 브랜치 정리: `web_2` 를 팀 `main` 위에 얹는 작업을 언제 하나. A 의 Vercel 배포 전에 하는 것을 권한다(배포 브랜치가 main 이어야 팀원도 본다).
- 루트 `src/`(빈 껍데기)와 `web/` 중 무엇을 본체로 할지. 사용자 메모 "기준은 루트 앱"과 실태가 반대.

## 의존성

- Supabase 계정·비밀번호(사람). 절차는 `web/db/README.md` "Supabase 로 옮길 때" 1~5 그대로.
- Vercel 환경 변수 `DATABASE_URL`·`HASH_SALT`(사람).
- 사진은 Supabase Storage 로 옮기지 않으면 Vercel 에서 사라진다 — A 안에서 사진 없는 등록을 허용하거나(`MIN_PHOTOS` 0) Storage 이전을 먼저 한다. 권장: 2주 안에는 `MIN_PHOTOS=0` 으로 열고 Storage 는 그다음.
- 정리 작업은 별도 보고서: 기술 검토 보고서(2026-11-09) 8절 순서대로, A 와 충돌 없음.

## 과제 (이번 주 안에 할 실제 행동 하나)

**청년부 단톡에 한 줄 올리기: "자주 가는 떡볶이집 3곳만 알려 주세요 (동네·가게 이름)".** 답이 10명에게서 오면 가게 30곳이고 그게 첫 핀이다. 답이 2명이면 그것도 답이다 — 청년부에 이 지도가 필요한지를 2주 코딩 없이 안 것이다. 받은 가게는 `/register` 로 직접 넣는다(등록 화면이 실제로 쓸 만한지도 같이 보게 된다).

## 세션에서 보인 것

- "3청은 우리 교회 청년부 말하는거야. 이 부분은 신경안써도되" — 대상이 누구인지는 분명히 알고 있다. 다만 그 안의 한 사람을 고르는 건 피했다. 다음에 그 한 사람 이름이 나오면 설계가 한 단계 더 좁아진다.
- 전제 1 에 "부분 동의" — 흔한 "동의"가 아니라 조건을 달았다. 게시판이 팀을 모은다는 가설은 타당하고, 그래서 C 를 버리지 않고 A 다음 후보로 남겼다.
- "이제 그만 물어보고 진행상황알려줘" — 결정보다 결과를 원하는 속도감. 이 문서가 그 요구에 맞게 묻지 않고 제가 판단한 부분(전제 2·3, 대안 선택)은 위에 "사용자 확인 전"으로 표시했다.
- "1차 MVP 라 사용자가 없는 게 당연하다. 이제 배포하고 쓰게 할 예정" — 제 진단이 "사용자 0"을 문제로 세운 것을 바로잡았다. 맞는 지적이라 문제 정의를 "배포를 막는 것"으로 다시 썼다. 방향(A)은 같다.
