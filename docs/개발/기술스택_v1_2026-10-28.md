# 떡볶여지도 기술 스택

## 1. 개요

떡볶여지도는 Next.js 앱 하나다. 저장소 루트가 앱 본체이고, 사용자 화면(`src/app/(site)/`), 운영 어드민(`src/app/admin/`), 쓰기 API(`src/app/api/*`)가 같은 앱 안에 있다. 이용자 로그인은 없고, 같은 사람은 기기 표시와 접속 IP로 가른다. 저장은 `DATABASE_URL` 이 없으면 서버 폴더의 JSON 파일(`.data/db.json`), 있으면 Postgres다. 사진은 Supabase Storage 설정이 있으면 Storage, 없으면 서버 폴더에 둔다. 지금은 이 컴퓨터의 파일 또는 도커 Postgres(PostGIS)로 돈다. 배포·DB 목표는 Vercel + Supabase이고, 아직 연결 전이다.

**확정된 결정**

- 배포는 Vercel, DB는 Supabase(Postgres + PostGIS)
- 앱 하나(모듈형 모놀리스). 서비스로 쪼개지 않는다
- 쓰기는 서버만 한다. 브라우저는 DB에 직접 붙지 않는다
- Next.js Cache Components를 켠다. 데이터는 기본이 동적이고, 캐시는 필요한 곳에만 `"use cache"` 로 둔다
- 패키지 매니저는 pnpm만 쓴다
- 사진은 Supabase Storage 비공개 버킷에 두고, 올리기와 내려받기는 앱 서버를 거친다
- 도배 방지는 판정의 무게로 나눈다. 내리는 판정(달라요·신고)은 서로 다른 IP 3곳, 좋은 쪽 판정(맞아요·평가·추천)은 기기, 하루 한도는 한 사람 한도 + 같은 IP 상한이다. 공개 전에 Turnstile을 붙인다
- 기기 표시는 localStorage UUID를 `x-ddy-device` 헤더로 보내는 방식을 유지하고, 기기 표시가 없는 쓰기는 거절한다
- 예시 데이터는 앱에 없다(11-19 에 뺌. 시험 자료는 `tests/fixtures/`). 실제 가게는 어드민 「후보 가져오기」로 넣는다
- 운영 데이터가 생기기 전까지는 표가 바뀌면 Supabase 에서 표를 지우고 `db/init/*.sql` 을 다시 돌린다(`db/README.md` 「표가 바뀌면」)

## 3. 아키텍처

```
[브라우저]
  │ 화면 요청 (GET)
  │ 쓰기: send() → POST /api/* (application/json, 헤더 x-ddy-device)   src/lib/me.ts
  │ 사진: uploadPhoto() → POST /api/photos (JPEG, 1280px, 헤더 x-ddy-device)
  │ 지도 타일: OpenFreeMap 직접 / 네이버 지도 스크립트 직접(키 있을 때)
  ▼
Next.js 앱 (지금: 개발 서버 / 목표: Vercel)
  ├ 화면 (서버 컴포넌트, connection() 으로 요청마다 읽음)
  │    └ src/lib/data/index.ts  ── 예시 숨김·가려진 가게 거르기
  ├ route handler  src/app/api/stores · stores/[id] · room · lists · lists/[id] · me · photos · photos/[id]
  │    └ src/lib/request.ts  ── 쓰기 입구: readJson(출처 403 · JSON 아님 415 · 64KB 초과 413)
  │                              → whoFrom(기기 표시 없으면 400) → 응답 모양(reply)
  ├ 어드민 Server Action  src/app/admin/actions.ts
  │    └ adminAccess() 매번 → src/lib/data/admin.ts → revalidatePath("/", "layout")
  ▼
src/lib/data/db.ts  ── 규칙 검사와 쓰기가 지나가는 길 하나 (load / mutate)
  │    판정: 한 사람 한 번 = 기기 + IP · 내림 = 서로 다른 IP 3곳 · 하루 한도 = 한 사람 + 같은 IP 상한
  ├ DATABASE_URL 없음 → .data/db.json
  └ DATABASE_URL 있음 → src/lib/data/pg.ts → Postgres (Supabase pooler · CI 의 Postgres)
src/lib/data/photos.ts  ── 사진을 두는 곳을 정하는 파일 하나 (DB 에는 사진 id 만)
  ├ SUPABASE_URL · SUPABASE_SERVICE_ROLE_KEY 있음 → Supabase Storage 비공개 버킷 <id>.jpg
  ├ 없음 → DATA_DIR/photos/<id>.jpg (서버 폴더)
  └ Vercel 이고 없음 → 올리기 거절(503)
```

- **읽기**: 화면은 `src/lib/data/index.ts` 로만 읽는다. 읽기 함수는 `db.ts` 의 `shared()` 를 부르고, `shared()` 는 `React.cache` 로 감싼 `load()` 다. `load()` 는 저장소 전체(표 13개)를 한 번에 읽어 앱에서 거른다. 지도 홈은 레이아웃(`(site)/(map)/layout.tsx`)에서 가게 전체와 최근 7일 등록·수정 수를 읽고, 가게 상세는 여기에 가게 하나와 평가를 더 읽는다. 화면 요청 하나에서 `load()` 는 한 번 돈다.
- **쓰기(이용자)**: 화면의 `send()` 가 `/api/*` 로 JSON을 보낸다. route handler는 `readJson()` 으로 출처·형식·크기를 검사하고, `whoFrom()` 으로 닉네임·기기·IP를 읽고, `wiki.ts`·`community.ts` 규칙으로 입력을 검사한 뒤 `db.ts` 의 쓰기 함수를 부른다. 쓰기는 `mutate()` 하나로 지나간다. 파일 모드는 프로세스 안 대기열로 한 번에 하나씩, PG 모드는 `pg_advisory_xact_lock` 트랜잭션 안에서 전체를 읽고 → 규칙대로 고치고 → 바뀐 줄만 넣기·고치기·지우기 한다.
- **쓰기(어드민)**: `/admin` 화면이 Server Action(`actions.ts`)을 부른다. 액션마다 `adminAccess()` 로 권한을 다시 확인하고, 성공하면 `revalidatePath("/", "layout")` 을 부른다. 실제 저장이 되는 어드민 화면은 로그인, 가게 관리(`/admin/stores`), 가게 편집·직접 등록(`/admin/stores/[id]`), 후보 가져오기(`/admin/candidates`), 운영 기록(`/admin/logs`)이다. 시안이던 홈·신고·요청·신선도·설정 다섯 화면은 11-19 에 지웠고 `/admin` 은 가게 관리로 넘긴다.
- **사진**: 브라우저가 긴 쪽 1280px JPEG로 다시 만들어 `POST /api/photos` 로 보낸다. 서버는 출처(`checkOrigin`)·기기 표시·3MB 이하·JPEG 머리 글자를 확인하고, 하루 한도 자리를 잡은 뒤(`photo_uploads`) `photos.ts` 의 `addPhoto()` 로 저장한다. 저장에 실패하면 잡은 자리를 돌려준다. `GET /api/photos/[id]` 가 Storage 또는 서버 폴더에서 읽어 1년 캐시 헤더로 내보낸다. 사진 주소와 id는 저장 위치와 상관없이 같다.
- **지도**: `TteokMap.tsx` 가 MapLibre로 대동여지도 느낌 바탕(OpenFreeMap 벡터 타일)을 그린다. 줌 14(`PRELOAD_ZOOM`) 이상이면 밑에 실제 지도를 깐다(`realMap.ts`). `NEXT_PUBLIC_NAVER_MAP_KEY_ID` 가 있으면 네이버 지도 GL, 없거나 인증이 실패하면(`navermap_authFailure`) OpenFreeMap 상세(liberty) 지도다. MapLibre 일꾼 파일은 `predev`·`prebuild` 가 `public/maplibre/` 로 복사한다.
- **주소 리다이렉트**(`next.config.ts`): `/report` → `/register`, `/together` → `/`, `/share*` → `public/share/` 의 `index.html`.

## 4. 데이터와 저장

**저장 경로 두 개** (`src/lib/data/db.ts`)

| 조건 | 저장 위치 | 쓰기 직렬화 |
| --- | --- | --- |
| `DATABASE_URL` 없음 | `DATA_DIR/db.json`. `DATA_DIR` 기본값은 `.data` | 프로세스 안 대기열, 임시 파일에 쓰고 이름 바꾸기 |
| `DATABASE_URL` 있음 | Postgres (`pg.ts`) | `pg_advisory_xact_lock(724242)` 트랜잭션 |

- Vercel(`VERCEL` 있음)에서 `DATABASE_URL` 이 비어 있으면 `db.ts` 를 불러올 때 오류를 던져 서버가 시작하지 않는다. `HASH_SALT` 도 같다.
- `pg.ts` 연결: 호스트가 `127.0.0.1`·`localhost`·`db` 면 로컬로 보고 ssl 끔·연결 5개. 그 밖은 바깥 DB로 보고 `ssl: "require"`·연결 1개·쉬는 연결 20초 뒤 반환. 포트가 6543(Supabase Transaction pooler)이면 미리 준비한 질의(prepare)를 끈다. 연결 수는 `DATABASE_POOL` 로 바꾼다.
- 빈 저장소: 파일 모드는 파일이 없으면, PG 모드는 표가 모두 비면 빈 저장소로 시작하고 아무것도 써 넣지 않는다. 예시 데이터는 앱에 없다. 시험은 `tests/fixtures/seed.ts` 가 `DATA_DIR` 에 시험 자료(가게 16곳·글·리스트)를 써 두고 돈다.
- 실제 가게 자료: 리서치 JSON 두 묶음(`stores-gangnam.json` 26줄, `stores-mapo.json` 19줄, `datasets.ts`)을 어드민 「후보 가져오기」로 넣는다. 빈 칸이 남은 줄(강남 4, 마포 5)은 「채워서 등록」으로 연다.

**표 13개** (`db/init/*.sql`, 새 DB에서 차례로 돈다)

| 파일 | 내용 |
| --- | --- |
| `001_schema.sql` | `stores`, `store_logs`, `reviews`, `store_votes`, `store_flags`, `posts`, `post_comments`, `post_likes`, `place_lists`, `list_likes`, `photo_uploads`(사진 하루 한도), `deleted_writes`(지운 글·댓글·리스트의 하루 한도 줄) (12개) |
| `002_postgis.sql` | PostGIS를 `extensions` 스키마에 설치, `stores.location`(geography) 칸과 lat·lng 변경 시 채우는 트리거, GIST 색인, 함수 `stores_in_bounds`·`stores_near` |
| `003_rls.sql` | 001의 12개 표에 RLS 켬, 허용 규칙(policy) 0개 |
| `004_directions.sql` | `store_directions`(길찾기 누름 기록) + RLS 켬 |

- 표가 바뀌면: 이미 쓰던 DB를 고치는 스크립트는 없다. 운영 데이터가 없는 동안은 Supabase 에서 표를 지우고 `db/init/*.sql` 을 다시 돌린 뒤, 가게는 어드민 「후보 가져오기」로 다시 넣는다. 표가 하나라도 없으면 앱이 DB를 읽지 못한다(13개를 질의 하나로 읽는다). 운영 데이터가 생긴 뒤에는 표를 지울 수 없다.
- 앱은 `location` 칸과 PostGIS 함수를 쓰지 않는다. 화면 범위·거리 계산은 앱이 전체를 읽은 뒤 한다. `pg.ts` 는 `location` 을 읽지도 쓰지도 않고 트리거가 채운다.
- RLS: 모든 표에 RLS가 켜져 있고 허용 규칙이 없어, Supabase 공개 키(anon·authenticated, Data API)로는 읽기·쓰기가 모두 막힌다. 앱은 표 주인 계정(`DATABASE_URL`)으로 서버에서만 붙으므로 RLS를 건너뛴다.
- 이용 기록: 길찾기 두 버튼(네이버·카카오) 누름만 `store_directions` 에 남는다. 같은 사람·같은 가게·같은 날은 한 줄이다.
- `photo_uploads` 와 `deleted_writes` 는 하루 한도를 세는 데만 쓴다. 최근 24시간 줄만 남기고, 줄을 더할 때 오래된 줄을 지운다.

**같은 사람 판정** (`src/lib/request.ts`, `src/lib/data/db.ts`)

- 브라우저는 처음 열 때 `crypto.randomUUID()` 로 기기 표시를 만들어 localStorage(`ddy-me`)에 닉네임과 함께 둔다. 쓰기 요청마다 `x-ddy-device` 헤더로 보낸다.
- 서버는 `x-ddy-device`(64자까지)와 IP(`x-forwarded-for` 첫 주소, 없으면 `x-real-ip`, 없으면 `local`)를 읽는다. 기기 표시가 없거나 `no-device` 인 쓰기는 400으로 거절한다.
- 둘 다 `sha256(HASH_SALT:값)` 앞 24자로만 저장하고 화면에 내보내지 않는다.
- `HASH_SALT` 가 비면 기본값 `ddy` 를 쓴다. Vercel에서 비어 있으면 서버가 시작하지 않는다.

| 판정 | 기준 |
| --- | --- |
| 한 사람 한 번(맞아요·달라요 한 표, 신고 한 번, 평가 하나, 「아직 있어요」 하루 한 번, 길찾기 하루 한 줄) | 기기 해시와 IP 해시가 모두 같으면 같은 사람 |
| 맞아요로 확인 완료 | 표 수 3. 같은 IP여도 기기가 다르면 각각 한 표 |
| 내리는 판정(달라요로 내림, 가게 신고로 내림, 후기·글·댓글 가림) | 서로 다른 IP 3곳(`HIDE_AT`). 같은 IP에서 기기 표시만 바꾼 요청은 한 곳으로 센다 |
| 하루 한도 | 한 사람(기기 + IP) 한도 + 같은 IP 전체 상한 |
| 추천(글·리스트) | 기기당 한 번, 다시 누르면 취소 |
| 「내 것」(리스트·글·댓글 고치기·지우기, `GET /api/me`) | 기기 표시만 |

## 5. 보안과 도배 방지

지금 코드에 있는 장치다.

- **쓰기 경로**: 쓰기는 route handler와 어드민 Server Action만 한다. 브라우저에 DB 주소·키가 가지 않는다. `NEXT_PUBLIC_` 값은 `SITE_URL`·`NAVER_MAP_KEY_ID` 둘이다. Supabase service role 키는 `photos.ts` 가 서버에서만 읽는다.
- **쓰기 입구 검사**(`request.ts` 의 `readJson`·`checkOrigin`): JSON 쓰기 route handler 다섯 개가 `readJson()` 을 지난다. `Origin` 의 host가 요청 주소(`X-Forwarded-Host`·`Host`·요청 URL) 또는 `NEXT_PUBLIC_SITE_URL` 과 다르면 403, `Origin` 이 없고 `Sec-Fetch-Site` 가 `same-origin` 이 아니면 403, `Content-Type` 이 `application/json` 이 아니면 415, 본문이 64KB를 넘으면 413이다. `Origin` 과 `Sec-Fetch-Site` 가 둘 다 없는 요청(브라우저가 아닌 요청)은 통과한다. 사진 올리기는 `checkOrigin()` 과 3MB 한도를 쓴다.
- **기기 표시**: `x-ddy-device` 가 없는 쓰기와 사진 올리기는 400이다.
- **IP**: `x-forwarded-for` 첫 주소를 쓴다. Vercel은 이 헤더를 실제 접속 주소로 덮어쓴다. 앞에 프록시가 없는 서버(`pnpm dev`·`pnpm start` 를 밖에 바로 열 때)에서는 요청한 쪽이 이 헤더를 지어 보낼 수 있다.
- **입력 검사**: `checkNewStore`·`checkPatch`·`checkReview`·`checkIntro`(`wiki.ts`), `checkPost`·`checkComment`·`checkListInfo`(`community.ts`). 소개글은 500자, 전화번호·링크를 막는다. 사진 id는 UUID 모양만 받는다.
- **중복 가게**: 80m 안에 같은(포함하는) 이름이 있으면 등록을 막고 그 가게 id를 돌려준다.
- **하루 한도**(최근 24시간, 한 사람 한도 / 같은 IP 상한): 등록·수정 합쳐 10 / 50, 글 20 / 50, 댓글 60 / 150, 리스트 20 / 50, 사진 30 / 150. 글·댓글·리스트는 지운 것도 센다(`deleted_writes`). 사진 한도는 `photo_uploads` 표에 남아 서버가 새로 떠도 이어서 센다. 넘으면 429다.
- **자동 내림**: 달라요를 낸 서로 다른 IP가 3곳이면(확인 중 가게만: 등록 7일 안·맞아요 3 미만) 가게를 `hidden` 으로, 가게를 신고한 서로 다른 IP가 3곳이면 `hidden`(폐업 신고 IP가 과반이면 `closed`)으로 바꾼다. 후기·글·댓글은 신고한 서로 다른 IP가 3곳이면 숨긴다. 지우지 않으며 어드민에서 되살린다. 운영자가 되살린 가게는 되살린 뒤의 달라요·신고만 센다.
- **내린 까닭**: 지도가 가게를 내릴 때 이력(`store_logs`)에 「내린 까닭」(달라요·신고)을 남기고, 가게 상세의 안내 문구(`wiki.ts` 의 `goneNotice`)가 이 값을 읽는다.
- **내려간 가게**: `hidden`·`closed` 가게는 맞아요·달라요, 「아직 있어요」, 평가를 받지 않는다(409). 정보 고치기와 신고는 받는다.
- **어드민 접근**(`src/lib/admin/access.ts`): `ADMIN_KEY` 가 있으면 `/admin/login` 에서 같은 열쇠를 넣은 브라우저만 들어간다. 쿠키 `ddy_admin` 은 열쇠의 HMAC-SHA256, `httpOnly`·`sameSite: strict`·12시간이고, Vercel production에서만 `secure` 다. 열쇠 비교는 길이·`timingSafeEqual` 로 하고 로그인 시도마다 0.6초 늦춘다. `ADMIN_KEY` 가 없으면 `VERCEL` 이 없고, `NODE_ENV` 가 production이 아니고, DB가 파일이거나 로컬 호스트이고, 요청 `Host` 헤더가 `127.0.0.1`·`localhost`·`[::1]` 일 때만 열린다. production(`next start`·도커 앱·Vercel)은 `ADMIN_KEY` 가 없으면 늘 잠긴다. `robots.txt` 는 늘 `/admin` 을 막는다.
- **어드민 화면 잠금**(`src/components/admin/AdminGate.tsx`): 모든 어드민 화면의 내용이 `adminAccess()` 뒤에 있다. 잠기면 머리글의 제목·설명과 잠김 안내만 나오고, 머리글의 단추·링크는 `AdminOnly` 가 그리지 않는다. 권한은 레이아웃이 아니라 화면과 Server Action마다 확인한다.
- **Server Action**: Next.js가 Origin과 Host를 비교해 다른 호스트의 호출을 막는다.
- **위치**: 「아직 있어요」 200m 거리는 기기 안에서 재고 좌표를 서버로 보내지 않는다.
- **사진 메타데이터**: 브라우저에서 캔버스로 다시 만들어 촬영 위치 등이 지워진 JPEG만 올린다.
- **사진 저장**: Storage 버킷은 비공개이고, 서버가 service role 키로 올리고(`x-upsert: false`) 내려받아 `/api/photos/<id>` 로 전달한다. Vercel에서 Storage 설정이 없으면 올리기를 503으로 거절한다.

## 6. 캐시와 성능

- 사용자 화면은 모두 `await connection()` 뒤에 데이터를 읽어 요청마다 새로 그린다. 데이터 캐시는 없다.
- 저장소 읽기는 화면 요청 하나에 한 번이다. `db.ts` 의 `shared()` 가 `React.cache` 로 `load()` 를 감싸, 레이아웃·페이지가 각각 읽어도 한 번만 돈다. 쓰기(`mutate`)가 끝나면 세대 번호가 올라 같은 요청의 다음 읽기는 새로 읽는다. React가 그리는 중이 아닌 곳(route handler)에서는 부를 때마다 읽는다.
- 어드민 읽기(`admin.ts` 의 `adminReadStores`·`adminReadStore`·`adminReadLogs`)는 `load()` 를 직접 불러 부를 때마다 저장소를 읽는다. 가게 편집 화면은 한 요청에 2번 읽는다.
- 저장소 읽기는 매번 표 13개 전체이고, PG 모드는 이것을 `json_build_object` 질의 하나로 가져온다. 쓰기는 전역 잠금 하나로 한 번에 하나씩 지나가고, 쓰기마다 전체를 읽는다.
- `"use cache"` 는 `generateMetadata` 다섯 곳에만 있다: 가게 상세(`/store/[id]`), 떡볶이방 글(`/room/[id]`), 맛집 리스트(`/lists/[id]`), 동네 목록(`/seoul/[gu]`), 지역·취향 목록(`/seoul/[gu]/[taste]`). `cacheLife`·`cacheTag` 가 없어 기본 프로필을 쓴다.
- `revalidatePath("/", "layout")` 은 어드민 저장 성공 때만 부른다. 이용자 쓰기는 캐시를 비우지 않는다.
- `sitemap.ts` 는 요청 시점 API를 쓰지 않아 빌드 때 가게 목록으로 고정된다.
- `generateStaticParams` 가 가게 상세·동네·지역·취향 목록에 있다.
- 지도 홈은 가게 전체를 내려보내되 소개글 등 긴 칸은 뺀다. 가게 검색·필터·범위 거르기는 브라우저에서 한다.
- 사진 응답은 `cache-control: public, max-age=31536000, immutable` 이다. Storage에서 읽을 때도 앱 서버가 받아서 전달한다.

## 8. 배포: Vercel + Supabase

**지금 상태**

- Vercel 프로젝트(`jltldud-5453s-projects/tteokbokki-yeojido`)에 CLI로 손수 올린 배포가 있다. 깃허브 자동 배포 연결은 없다. 저장소에 `vercel.json` 은 없고 `.vercelignore` 가 `.data` 를 뺀다.
- 지금 코드는 Vercel에서 `DATABASE_URL` 또는 `HASH_SALT` 가 비어 있으면 시작하지 않는다.
- Supabase 프로젝트와 Storage 버킷은 없다. 옮길 SQL(`db/init/001~004`), DB 연결 코드(`pg.ts`), 사진 저장 코드(`photos.ts`)는 있다.
- 배포와 같은 빌드는 `pnpm build && pnpm start` 로 띄운다. production이라 `ADMIN_KEY` 가 없으면 어드민이 잠긴다. 도커 앱 서버(`pnpm app:up`)는 11-19 에 지웠다.

**연결 절차** (`db/README.md` 「Supabase 로 옮길 때」 요약)

1. Supabase 새 프로젝트를 서울(Northeast Asia, Seoul) 지역으로 만들고 DB 비밀번호를 정한다.
2. SQL Editor에서 `001_schema.sql` → `002_postgis.sql` → `003_rls.sql` → `004_directions.sql` 을 차례로 실행한다.
3. Connect → Transaction pooler 주소(포트 6543)를 `DATABASE_URL` 로 쓴다. Direct connection(5432)은 IPv6라 Vercel에서 붙지 않는다.
4. 이 컴퓨터의 `.env.local` 에 그 주소를 넣고 개발 서버로 읽기·쓰기를 확인한다.
5. Storage에서 사진 버킷을 비공개로 만든다. 이름은 `photos`, 다르면 `SUPABASE_PHOTO_BUCKET` 에 적는다. `.env.local` 에 `SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY` 를 넣고 사진을 올려 버킷에 `<id>.jpg` 가 생기는지 확인한다.
6. Vercel 환경 변수에 `DATABASE_URL`·`HASH_SALT`·`SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY`·`ADMIN_KEY` 를 넣고 다시 배포한다. Vercel 함수 기본 지역은 미국이고 DB는 서울이다.
7. 빈 DB에 실제 가게를 넣는다: `/admin/login` → `/admin/candidates` 「후보 가져오기」 → `/admin/stores` 에서 확인.

**환경 변수** (`.env.example` 기준, `VERCEL`·`NODE_ENV` 는 코드가 읽는 값)

| 이름 | 쓰는 곳 | 비었을 때 | Vercel 운영 |
| --- | --- | --- | --- |

| 2 | Supabase 프로젝트와 Storage 버킷이 없다. Storage 올리기·내려받기는 가짜 `fetch` 단위 시험으로만 확인했다 | 프로젝트·비공개 버킷을 만들고 실제 버킷에 올리기·내려받기를 확인한다 |
| 3 | 표를 바꾸는 방법이 「지우고 다시 만들기」뿐이다. 운영 데이터가 생긴 뒤에는 쓸 수 없다 | 표 설계를 연결 전에 마치고, 연결 뒤 표를 바꾸는 방식을 정한다(「열린 질문」) |
| 4 | 요청마다 저장소 전체(표 13개)를 읽는다. 화면 요청은 한 번, 쓰기는 쓰기마다 한 번, 어드민 읽기는 부를 때마다 읽는다. 쓰기는 전역 잠금 하나로 줄 선다. 화면 범위·거리 계산은 앱에서 한다 | 화면별로 필요한 것만 읽게 한다(화면 범위 조회는 「열린 질문」) |
| 5 | 앞에 프록시가 없는 서버(`next start` 를 밖에 바로 열 때)에서는 `x-forwarded-for` 를 요청한 쪽이 지어 보낼 수 있고, IP 기준 판정(내림 3곳·IP 상한)이 그 값을 쓴다. Vercel에서는 헤더가 덮어써진다 | Vercel 밖에서 운영하면 이 헤더를 덮어쓰는 프록시 뒤에 둔다 |
| 6 | E2E가 CI에서 돌지 않는다. E2E는 파일 모드로만 돈다 | CI에 E2E를 넣는다 |
| 7 | 등록에 필요한 사진 수(`wiki.ts` 의 `MIN_PHOTOS`)가 0이다 | Storage 연결 뒤 값을 정한다(「열린 질문」) |
| 8 | (11-19 해소) 예시 데이터를 앱에서 빼서 운영 화면에 예시 가게가 나올 길이 없다 | 운영 빌드에 `NEXT_PUBLIC_SITE_URL` 을 넣는다 |

## 10. 열린 질문

- **어드민 로그인**: `ADMIN_KEY` 열쇠 유지 / Supabase Auth(이메일 링크 + 관리자 목록 표)
